# WeatherShmeather iOS Architecture

How the Swift app is organized. The iOS project lives at the repository root, beside `docs/`. This is the engineering guide for whoever builds or reads the iOS client: the build pipeline, the module layout, the dependency injection, and the layering from managers up to screens.

WeatherShmeather exists to demonstrate an iOS app architecture, not to be a great weather app. The product is deliberately small so that every architectural idea has exactly one clear, readable example. When a choice is between "simplest weather feature" and "clearest demonstration of the pattern", the pattern wins, and this document says so where it happens.

Last updated: 2026-11-11

The short version: **a single SwiftPM package of many small targets, generated by Velocity, where every manager and every screen is a protocol module plus an Impl module, wired by generated injection, and every screen is a UIKit view controller hosting a SwiftUI leaf. Per-user isolation comes from rebuilding the whole injection container around a per-user `AppEnvironment`.**

All upstream Swift packages are declared in `dependencies.yml` and vendored into `local/Packages/` by Velocity. These are the ones that define the architecture:

| Package | Role |
|---|---|
| `jmfieldman/Inject` | Dependency injection: `Inject()`, `InjectionManager`, `Builder`, `BuilderManager`, `MainActorBuildable`. |
| `jmfieldman/SwiftAsyncEx` | Reactive and async primitives: `Property` / `MutableProperty` / `PropertyProtocol`, `PersistentProperty` with file and keychain storage engines, `SerialTask`, `Task.observe`, `Task.bound(to:)` / `TaskBag`, `LoadableResult`. |
| `jmfieldman/SwiftUIEx` | The screen scaffolding: `HostingScreen`, `HostingScreenModel`, `HostedView`, plus `RequirementCoordinator` for gated flows. |
| `jmfieldman/Slate` | The local store for tabular data, with `@SlateEntity` declarations and generated bridges. See Persistence. |

| `SFSafeSymbols/SFSafeSymbols` | Type-safe SF Symbols. Lint forbids string symbol names. |

There are no third-party SDKs beyond these, and no API keys: Open-Meteo is free and keyless for non-commercial use.

CLI tools are pinned in `Mintfile` and run through `mint`: SwiftFormat, SwiftLint, XcodeGen, Velocity, and Slate's generator, at the same version as the Slate package. Nothing is installed globally by hand. No Combine, no ReactiveSwift, no third-party networking, no SwiftData, and no generated mocks.

## Build system

The Xcode project is a generated artifact, never the source of truth.

```
dependencies.yml ──velocity pull-dependencies──▶ local/Packages/, .project-dependencies.yml
Modules/**/.package.yml + *.swift ──velocity generate-imports──▶ Modules/**/.imports.yml
                                  ──velocity generate-inject───▶ Modules/Injection/Injection/Injection.swift
                                  ──velocity generate-resources▶ <Name>Resources/*.swift shims
                                  ──velocity generate-package──▶ Modules/Package.swift
project.yml + .project-app.yml + .project-dependencies.yml ──xcodegen──▶ WeatherShmeather.xcodeproj
```

Everything goes through `Makefile`:

| Target | When |
|---|---|
| `make bootstrap` | Once per machine: installs Mint, the pinned tools, the git hooks, then runs `make`. |
| `make` | After every pull or branch switch: pull dependencies, format, regenerate the project. |
| `make modules` | After adding, renaming, or removing a module, or changing imports: imports, injection, resources, package. |
| `make project` | Regenerate and reopen the `.xcodeproj` (closes the running Xcode instance first). |
| `make pulldeps` | After editing `dependencies.yml`. |
| `make format` | SwiftFormat on changed files; the pre-commit hook runs it too. |
| `make test` | Runs the module test targets on the simulator. |
| `make models` | After changing a `@SlateEntity` model: regenerates the Slate bridges and schemas. |

Three safety nets keep generated files correct so a developer only edits Swift and commits: the Xcode scheme's pre-build script (`bin/scripts/prebuild.sh`) regenerates resources, imports, and formatting on Debug builds when inputs changed; the pre-commit hook regenerates `.imports.yml` and `Injection.swift`, re-stages them, and runs SwiftFormat and SwiftLint; and `make` on checkout realigns dependencies. Generated files that are small and diffable (`Package.swift`, `.imports.yml`, `Injection.swift`, resource shims, Slate's generated bridges) are committed so a fresh clone builds before bootstrap; bulky ones (`local/Packages/`, the `.xcodeproj`, `.cache/`) are gitignored.

Settings that are locked in: Swift 6.2 with strict concurrency, warnings as errors on every target, `DEAD_CODE_STRIPPING`, user-script sandboxing on, iOS 26 as the deployment floor (`.iOS(.v26)` and `IPHONEOS_DEPLOYMENT_TARGET: 26.0`). `Observations` is therefore always available, but `Task.observe` stays the house helper so all reactive glue has one shape.

## Module layout

`Modules/` is one SwiftPM package. Every Swift target is a library sub-target of it, and the app target in `System/` is a thin shell whose only sources are `AppDelegate.swift` and `SceneDelegate.swift` and whose only package dependency is the `SceneDelegation` product.

```
Modules/
├── Package.swift                 generated
├── Foundation/                   value types, extensions, helpers, design system, logging
│   ├── AppEnvironment/           who is signed in, where this user's files live
│   ├── DesignSystem/ (+DesignSystemResources/)  tokens and components
│   ├── Logging/                  Log(.context, .level, "message"), stored in Slate
│   ├── Models/
│   │   ├── NetworkModels/        NetworkRestResource, NetworkService, NetworkError
│   │   └── <Domain>Models/       domain value types and @SlateEntity models
│   ├── SceneDelegation/          SceneDelegator: the real app bootstrap
│   └── Extensions/               small third-party or SwiftUI extensions
├── Managers/                     injected @MainActor singletons, one group per manager
│   └── <Name>Manager/
│       ├── .package.yml          injects: _
│       ├── <Name>Manager/        protocol + domain types + error types   (the public API)
│       ├── <Name>ManagerImpl/    the class, NetworkResources/, Generated/
│       ├── <Name>ManagerResources/  optional assets and strings
│       ├── <Name>ManagerTestHelpers/  hand-written Mock<Name>Manager
│       └── <Name>ManagerTests/      tests for the Impl
├── UI/                           screens and reusable UI primitives
│   └── <Feature>UI/
│       ├── .package.yml          buildersAuto: true
│       ├── <Feature>UI/          one <Screen>Screen.swift per screen: protocol + Builder
│       ├── <Feature>UIImpl/      per screen: <Screen>ScreenImpl.swift (+ model) and <Screen>View.swift
│       └── <Feature>UIResources/ optional
├── Coordinators/                 multi-screen flows, same Abstract/Impl shape
└── Injection/
    └── Injection/Injection.swift generated
```

Three module archetypes, selected by the group's `.package.yml`:

- `mainOnly: true`. One flat target. Used for Foundation value types, extensions, the design system, dialog primitives, and anything with no implementation to hide.
- `injects: _`. An injected manager: a protocol target and an Impl target. Velocity emits the registration pair into `Injection.swift`.
- `buildersAuto: true`. A screen or coordinator group: an API target holding protocols and `Builder` structs, and an Impl target. Velocity emits a `BuilderManager` registration for every Builder it finds in the API target.

A Foundation module that needs tests or test helpers, such as `AppEnvironment`, has its own directory for each target and an empty `.package.yml` (`{}`), since a `mainOnly` group can hold only one.

`.imports.yml` files are generated from the `import` statements in each target's Swift and must never be hand-edited. The correct workflow for any dependency change is to write the `import`, then commit. Forgetting `.package.yml` is the one way a module silently fails to exist.

### The Abstract/Impl rule

Every manager, screen, and coordinator is two targets: a public protocol module that consumers import, and an Impl module that **only `Injection.swift` imports**. Consumers depend on protocols and Builders, never on implementations. This keeps the dependency graph a shallow tree, keeps incremental builds fast, and makes swapping an implementation a one-line change in generated code.

## Dependency injection

`Inject` resolves protocols to lazily constructed singletons from a process-wide registry. Three call sites, all generated or in `SceneDelegator`:

1. `InjectionManager.registerInjections()` and `BuilderManager.registerBuilders()` run once at scene connect, before anything is built.
2. `InjectionManager.activateInjections()` eagerly constructs every manager once a user session is ready, so first-interaction paths are warm.
3. Everywhere else: `let foo: FooManager = Inject()` as a plain `let` on the consumer.

Every Impl has a zero-argument `init()`; dependencies are `Inject()`ed fields, not constructor parameters. Managers inject other managers' protocols; screen models inject managers; nothing injects an Impl. The graph of managers must stay acyclic. SwiftPM only sees imports of protocol modules, so it can't catch a cycle through `Inject()`; Debug builds set `InjectionManager.detectResolutionCycles = true` to catch it at runtime.

### The session container

The injection container is **per user session**, and that is the single mechanism for per-user isolation. Showing this off is one of the main reasons the app exists.

- `AppEnvironment` is registered into the container with the current `userId` (or `nil` before sign-in). It derives everything scoped to that user: the document silo directory, the cache silo directory, the file-backed property store, and the keychain store.
- Every manager that holds per-user state reads `appEnvironment.userId` in `init` and opens its stores under that silo. A manager built with `userId == nil` runs in a transient mode (no per-user persistence, no auto-refresh).
- On sign-in and on sign-out the session coordinator calls `InjectionManager.resetCurrentContainer()`, re-registers `AppEnvironment` with the new user id, and lets the next `Inject()` rebuild every manager against the new environment. Nothing swaps a store in place; the whole manager layer is torn down and rebuilt, and the weather experience is rebuilt from its Builder.
- Screens hold their managers through `Inject()`ed fields, so an old manager lives exactly as long as the last screen that captured it. On log out the coordinator therefore resets the container only after the dismissal completes, and Debug builds check that the old session's managers are released afterwards. A leak there is a session-isolation bug, not just a memory one.

That is the only correctness obligation for user isolation. There is no view-hierarchy contract, no `.id(userId)` trick, and no shared store with a user predicate.

### "Signing in"

There is no server-side account and no password. Signing in means typing a username, and **the normalized username is the user id**. This keeps the demo free of auth plumbing while still exercising everything that matters about per-user environments: two people using the app on one device see entirely separate saved locations, settings, and caches, and switching between them tears down and rebuilds the manager layer.

- `SessionManager` owns the current user. The signed-in user's id and the last five usernames live in `PersistentProperty`s on the transient environment's store (`AppEnvironment.transient.propertyFileStore`, the environment with no `userId`), because they must be readable before any user's environment exists. That store is the only one that outlives a session. The two properties themselves live in a process-wide `SessionStore`, not on the manager: every session builds its own `SessionManagerImpl`, and two `PersistentProperty` instances for one key would each keep their own in-memory value, so a write through one would never reach observers of the other.
- Normalization (trimming, lowercasing, an allowed character set, a length limit) lives in one value type, `Username`, in the `SessionManager` API module, so the screen's validation and the silo directory name can never disagree.
- Logging out returns to the sign-in screen without deleting anything; signing back in as the same username restores that user's data.

## Layers

```
HostedView           SwiftUI leaf; pure function of its @Observable ViewModel
  ▲ reads state, fires closures and SerialTasks
ViewModel            @Observable @MainActor; plain values, closures, SerialTasks; previewable alone
  ▲ constructed and driven by
ScreenModel          @MainActor HostingScreenModel; Inject()s managers; async work; navigation via viewController
  ▲ owned by
ScreenImpl           HostingScreen subclass (a UIViewController); navigationItem; lifecycle
  ▲ built through
Builder              struct in the API module; the only thing other modules see
──────────────────────────────────────────────────────────────────────────────
Manager              @MainActor singleton; owns state and business logic; vends Property handles
  ▲
NetworkManager       request(resource:) async throws(NetworkError)
Persistence          per-user stores opened in the manager's init
```

Where decisions live: cross-screen state and business logic in managers; screen-local state, validation, loading, and error translation in the screen model; navigation in screen models (single pushes) and coordinators (flows), never in managers; persistence in managers only.

## Managers

The central abstraction. A manager is a `@MainActor` protocol in its API module and a `@MainActor final class` Impl that takes no constructor arguments.

```swift
@MainActor
public protocol ForecastManager: AnyObject, Sendable {
    func forecast(for placeId: Place.ID) -> any PropertyProtocol<LoadableResult<Forecast, ForecastError>>
    var refreshAll: SerialTask<Void, Void> { get }
}

@MainActor
public final class ForecastManagerImpl: ForecastManager {
    private let appEnvironment: AppEnvironment = Inject()
    private let networkManager: NetworkManager = Inject()
    private let slateManager: SlateManager = Inject()

    private let slate: Slate<ForecastSlateSchema>

    public private(set) lazy var refreshAll: SerialTask<Void, Void> = .weak(self) { owner in
        await owner.performRefreshAll()
    }

    public init() {
        self.slate = slateManager.provide(for: ForecastSlateSchema.self)
    }
}
```

Rules:

- **Reactive state is `MutableProperty` inside, `Property` outside.** Vend `any PropertyProtocol<T>` get-only members. The class itself is not `@Observable`.
- **Derived state is `Property(tracking:)`** reading other properties inside the closure. It recomputes on a later main-actor turn, not inside the write that changed its inputs, so a test waits briefly before reading it. Side effects on change use `Task.observe(of:perform:)`. Never inline `withObservationTracking`.
- **Long-lived tasks bind to the owner** with `Task.bound(to: self)` or `.bind(to: self)`, so they cancel when the manager is torn down at a user switch. No hand-rolled task arrays.
- **Repeatable async entry points are `SerialTask`s** (`refresh`, `search`). One in flight at a time; `fire()` coalesces, `run()` awaits. UI components bind to them directly.
- **Typed throws on every async method.** `async throws(ForecastError)`. Error types live in the API module and conform to `ErrorDialogProviding` so a screen can show them.
- **Transient versus per-user mode is decided in `init`** from `appEnvironment.userId`.
- **Heavy work goes to a plain `actor` or `Task.detached`** that pushes results into a MainActor `MutableProperty`. Do not make a manager a non-main global actor.
- **Managers never navigate.**

The managers, each chosen to show one pattern (features are in [PRODUCT.md](../PRODUCT.md)):

| Manager | Owns | Shows off |
|---|---|---|
| `NetworkManager` | Every HTTP request | Typed resources, typed errors |
| `SlateManager` | Vending Slate stores under the user silo | Per-user store routing |
| `SessionManager` | The signed-in username and the last five usernames, on the transient environment | Persistent properties that outlive a session; the container rebuild on sign-in and log out |
| `DeviceLocationManager` | CoreLocation permission and the device's location, as `Property` values | Wrapping a system callback API as reactive state |
| `PlacesManager` | The `StoredPlace` Slate table, including the one `isCurrentLocation` row, and place search | A flag row the manager overwrites as `DeviceLocationManager` reports moves of more than a kilometer, and deletes while permission isn't granted; a `SlateStream` republished as `places`; search as a plain typed-throws call that the screen model debounces |
| `ForecastManager` | Fetching and caching forecast and air-quality rows per place | Slate as a cache; observing `PlacesManager.places` to fetch new places and delete removed ones; freshness rules |
| `PreferencesManager` | One `PersistentProperty` per unit and display setting, defaulting to the device's region | Single values with `PersistentProperty`; `resolvedTemperatureUnit` and `unitSettings` derived with `Property(tracking:)`; a `WeatherFormatter` value built from `unitSettings` turns stored metric values into strings |

The graph is acyclic: `PlacesManager` depends on `DeviceLocationManager`, and `ForecastManager` depends on `PlacesManager`. `PreferencesManager` depends on nothing, and screens combine its settings with the canonical metric values when they format.

### Network resources

Each manager Impl owns a `NetworkResources/` directory with one file per endpoint. A resource is a `NetworkRestResource` conformer naming the method, the service, the path, and two **bespoke wire types**:

```swift
struct ForecastResponse: Decodable, Sendable { /* mirrors Open-Meteo's JSON exactly; times stay String */ }

struct GetForecastResource: NetworkRestResource {
    typealias Request = ForecastRequest       // query items: latitude, longitude, hourly=…, daily=…
    typealias Response = ForecastResponse
    let request: ForecastRequest
    let method: NetworkHTTPMethod = .get
    let service: NetworkService = .forecast
    let path = "/v1/forecast"
}
```

Rules: wire models are private to the manager Impl and mirror Open-Meteo's response field for field; Open-Meteo's columnar arrays (`hourly.time[]`, `hourly.temperature_2m[]`, …) are zipped into row-shaped domain values by a `Domain.init(response:)` extension in the Impl; the domain type the manager vends lives in the API module (or a shared `<Domain>Models` module) and never imports transport types.

`NetworkService` is an enum with one case per Open-Meteo host, since Open-Meteo splits its APIs across subdomains:

| Case | Base URL |
|---|---|
| `forecast` | `https://api.open-meteo.com` |
| `geocoding` | `https://geocoding-api.open-meteo.com` |
| `airQuality` | `https://air-quality-api.open-meteo.com` |

The version segment lives on the resource path. `NetworkManagerImpl` composes URL building (GET requests become query items), the `URLSession` call, status-code checking, and JSON decoding, and maps every failure into `NetworkError`, decoding Open-Meteo's `{"error": true, "reason": "…"}` body when there is one. It also feeds the in-app network log that the admin screen shows. Every request uses `appEnvironment.urlSession`, an ephemeral session that keeps no cookies or URL cache, so caching is always a manager's explicit decision. A manager maps a failure to its own typed error.

There is no auth header, token refresh, or forced logout: Open-Meteo is anonymous. Those layers are deliberately absent rather than stubbed.

## Screens

Every leaf screen is four pieces in an Impl module plus a Builder in the API module.

```swift
// API: Modules/UI/WeatherUI/WeatherUI/PlaceForecastScreen.swift
public protocol PlaceForecastScreen: UIViewController, MainActorBuildable {}
public struct PlaceForecastScreenBuilder: Builder {
    public typealias BuildResult = PlaceForecastScreen
    public let placeId: Place.ID
    public init(placeId: Place.ID) { self.placeId = placeId }
}

// Impl: Modules/UI/WeatherUI/WeatherUIImpl/PlaceForecast/PlaceForecastScreenImpl.swift
@MainActor
public final class PlaceForecastScreenImpl: HostingScreen<PlaceForecastScreenModel, PlaceForecastView>, PlaceForecastScreen {
    public convenience init(builder: PlaceForecastScreenBuilder) {
        self.init(controllerModel: PlaceForecastScreenModel(placeId: builder.placeId))
    }
}

@MainActor
public final class PlaceForecastScreenModel: HostingScreenModel {
    public weak var viewController: UIViewController?          // must be weak
    public private(set) lazy var viewModel: PlaceForecastViewModel = .init(
        refreshTask: .weak(self) { `self`, _ in await self.refresh() },
    )
    private let forecastManager: ForecastManager = Inject()
    let placeId: Place.ID
    public init(placeId: Place.ID) { self.placeId = placeId }
}

// Impl: Modules/UI/WeatherUI/WeatherUIImpl/PlaceForecast/PlaceForecastView.swift
@Observable @MainActor
public final class PlaceForecastViewModel {
    public var title: String = ""
    public let refreshTask: SerialTask<Void, Void>
    public init(refreshTask: SerialTask<Void, Void>) { self.refreshTask = refreshTask }
}

public struct PlaceForecastView: HostedView {
    let viewModel: PlaceForecastViewModel
    public init(viewModel: PlaceForecastViewModel) { self.viewModel = viewModel }
    public var body: some View { /* tokens and DesignSystem components only */ }
}
```

What each piece may do:

- **Builder** (API): input parameters only. `build()` is inherited; registration is generated.
- **ScreenImpl**: forward the builder to the model, set `navigationItem`, lifecycle hooks. Nothing else.
- **ScreenModel**: the only place with `Inject()`, `try await`, error translation, and navigation. Constructs the ViewModel with `SerialTask.weak(self)` closures so the model is never retained by its own tasks. Observes manager properties and pushes values into the ViewModel.
- **ViewModel**: what a `#Preview` needs and nothing more. Values, closures, `SerialTask`s. No `Inject()`, no navigation.
- **View**: pure SwiftUI. Reads the ViewModel, fires its tasks, uses `@State` for purely local input. No `@Query`, no `@Environment` stores, no `NavigationStack` across screen boundaries, no manager access. Always ships with light and dark previews built from a bare ViewModel.

Naming: `FooScreen`, `FooScreenBuilder`, `FooScreenImpl`, `FooScreenModel`, `FooViewModel`, `FooView`. One `<Feature>UI` group can hold many screens; each gets its own `<Screen>Screen.swift` in the API target and a subdirectory in the Impl target.

A screen that genuinely needs hand-rolled UIKit subclasses `UIViewController` directly, keeps the Builder and the ScreenModel, and skips the SwiftUI leaf and ViewModel. The place pager is the example here: a `UIPageViewController` container whose pages are ordinary `PlaceForecastScreen`s built from their Builders.

### Dialogs

One-shot overlays are not screens. `Modules/UI/DialogUI/` presents a `DialogModel<Output>` as an alert or action sheet, with buttons rendered through `ActionButton`.

- `await viewController?.present(dialog:)` returns the chosen button's output, or nil if no choice was made. It always resumes, even if the dialog can't appear or something else removes it, and only after the dialog has left the screen. A one-choice dialog uses `DialogModel<Void>` and checks for nil.
- A button's work runs with a spinner in the button. If it throws, the dialog stays open, shows the error's `errorBody` inline, and lets the user retry or cancel.
- `DialogTextField` adds text entry: keep a reference and read `text` in a button's work. The first field takes focus.
- `.notice`, `.confirmation`, and `.error` cover the common dialogs. `present(error:)` reports a failed action from `ErrorDialogProviding`.
- `withProgressDialog(_:perform:)` is for work with no button to hold a spinner. Quick work shows nothing.

## Navigation

UIKit navigation, SwiftUI rendering. Screens are pushed, presented, and dismissed imperatively through the screen model's `viewController` back-reference, and the destination is always obtained from its Builder:

```swift
let next = PlaceForecastScreenBuilder(placeId: place.id).build()
viewController?.navigationController?.pushViewController(next, animated: true)
```

- A screen's Impl never imports another screen's Impl. Builders in API modules are the unit of cross-screen navigation.
The controller structure, from the window down:

```
UIWindow
└── RootViewController                root, always; never replaced
    ├── SignInScreen                  child; rebuilt on each log out
    └── (presented, full screen) UINavigationController     the weather experience
        ├── PlacesListScreen          base of the stack
        └── PlacePagerScreen          pushed above it, navigation bar hidden
            └── PlaceForecastScreen   one per page
```

- **The window's root is `RootViewController`**, a plain UIKit container that holds the sign-in screen as a child. It is never replaced. The sign-in screen inside it is rebuilt from its Builder every time the container returns to the transient environment, because its model captured the previous transient container's managers.
- **`SessionCoordinator`** owns the user-session lifecycle. On sign-in it resets the container, registers the new user's `AppEnvironment`, builds the weather experience from its Builder, and presents it full screen. On a cold launch with a signed-in user it does the same thing immediately, presenting without animation right after the window becomes visible, so the user never sees sign-in. On log out it dismisses the experience, then resets the container to the transient environment and installs a fresh sign-in screen. It also signals the `SceneDelegator` when managers may be activated.
- **Inside the weather experience**, the pager is pushed above the list without animation when there is a place to show. The pager's list button pops to the list, and tapping a card pushes the pager at that place. Sheets (Units) and menus are presented from the list screen.
- **Coordinators** live in `Modules/Coordinators/` and own multi-screen flows. A flow with gated steps uses SwiftUIEx's `RequirementCoordinator`, a list of "is this requirement satisfied, else show this screen" nodes; sign-in is simple enough that `SessionCoordinator` doesn't need one.
- SwiftUI navigation primitives (`.sheet`, a local `NavigationStack`) are allowed only inside a single screen for sub-flows that never leave it.

## App bootstrap

`System/AppDelegate.swift` and `System/SceneDelegate.swift` are nearly empty; `SceneDelegate` forwards to `SceneDelegator` in `Foundation/SceneDelegation`, which is the real entry point and the one place that knows about every top-level module. In order: register injections and builders, start the logger, build the sign-in screen as the window's root and make the window visible, install the admin gesture, build the session coordinator (which may present the weather experience at once), and observe its `readyForInjectionActivation` property to call `activateInjections()` on each false-to-true edge. Previews short-circuit before any of this.

## Persistence

Three tiers, chosen by shape. The weather domain was picked partly because it has natural examples of each:

| Shape | Mechanism | Owner | Examples here |
|---|---|---|---|
| A single value or a small struct that is read and saved whole | `PersistentProperty<T>` on the right storage engine: `appEnvironment.propertyFileStore` (per user), `propertyKeychainStore` (secrets), `AppEnvironment.transient.propertyFileStore` (outlives sessions) | The manager, vended as `Property(mirroring:)` | One property per unit and display setting; the signed-in user id and last five usernames (transient) |
| Tabular data | Slate, opened through `SlateManager` under the user silo | The manager; views never see the store | Places (saved and current location), cached current, 15-minute, hourly, daily, and air-quality rows, log entries |
| In-memory only | `MutableProperty<T>` in the manager | The manager | Location permission and position, in-flight load state |
| Screen-local | Values on the screen's ViewModel | The screen model | Search results while searching, edit mode |
| View-local, no observation beyond the view | `@AppStorage` or `@State` | The view | A collapsed section |

A Slate model is a `@SlateEntity` struct with `#Unique` and `#Index` declarations in `Foundation/Models/<Name>Models/`. `make models` runs `bin/scripts/gen_manager_model.sh <Name>`, which writes the mutable, bridge, and schema files into `<Name>ManagerImpl/Generated/`. Logging has its own script, and opens its store directly under the transient silo, because `SlateManager` depends on it. A manager gets its store with `slateManager.provide(for: <Name>SlateSchema.self)` in `init`. The default `.cacheStore` wipes and recreates a store whose schema no longer fits.

That wipe is fine for a pure cache, such as forecasts, which Open-Meteo can always resupply. Saved locations are different: they are user-created and exist nowhere else, so a schema change loses them. Every store still uses `.cacheStore` and there are no migrations. That loss is accepted as a demo simplification; a shipping app would open user-created data with `.strict` and write migrations.

Whatever the tier, the invariant is the same: **the manager owns the store, opens it from `AppEnvironment` in `init`, and republishes into its `MutableProperty`s after every write.** The simplest way to keep that promise is to observe a `SlateStream` of the rows, which Slate re-emits after each save, as `PlacesManager` does. Cross-manager references are by id, never by relationship.

## Design system

`Modules/Foundation/DesignSystem/` is token-driven and every screen composes from it. Three layers: an asset-catalog palette with light and dark variants, purpose-named semantic tokens in Swift (`DesignTokens.primaryAction`, `.screenBackground`, `TextStyle.body`, `CGFloat.m`, `Radius.control`, `ControlHeight.primary`, `RowHeight.standard`), and components built from tokens (`ActionButton`, `FormRow`, `AccessoryListItem`, and others). Text gets its font and color together from `.textStyle(_:color:)`; a `.foregroundStyle` after it has no effect, because the innermost foreground style wins. Rules a reviewer enforces: no hex colors, no `.font(...)` chains, no magic spacing numbers, no raw corner radii, no hand-rolled buttons where `ActionButton` fits, and palette entries never referenced from screen code. A missing token or component is added to `DesignSystem/`, not inlined. The visual language is flat (see PRODUCT.md, "Visual design"): typography, SF Symbols and color carry the design; system Liquid Glass appears only where UIKit and SwiftUI put it (toolbars, menus, sheets, search fields); and the tokens include a per-condition color treatment, not imagery.

## Logging and errors

- `Log(.context, .level, "message")` is the only logging call. `print` and `NSLog` are lint errors. Entries persist to a Slate store with a 24-hour prune and mirror to `os_log` in Debug; the admin screen can browse them. `LogContext` is a closed enum, one case per subsystem.
- Errors are typed enums per manager, thrown with `async throws(E)`, translated to user copy by the screen model through `ErrorDialogProviding`. Views never see a thrown error.
- `LoadableResult<T, E>` models screens that distinguish not-started from empty.

## Code style and lint

SwiftFormat and SwiftLint configs live at `.swiftformat` and `.swiftlint.yml`. Test functions stay camelCase (`--test-case-name-format preserve`). The notable custom rules: `localizedUppercase` over `uppercased()`, `lowercaseUUIDString` over `.uuidString`, `weak self` never `unowned self`, `Log()` over `print`, no `Image(systemName:)` (use SFSafeSymbols), no `UIImage(named:)` (use generated accessors), no `NSLocalizedString` (strings come from generated resource shims), no member-level imports, and `viewController`-style back references must be `weak`. SwiftLint runs in strict mode in the pre-commit hook.

## Admin and debug surface

`AdminUI` is reachable in non-App-Store builds by a triple tap on the window with two fingers, or with one in the simulator. It has a persistent-property browser, a log browser, and a network log. The network log keeps recent bodies in memory only and is off in App Store builds. Because there's no server environment to switch, the admin screen's natural extra here is a list of every user silo on the device with its size, which makes the per-user isolation visible.

## Testing

Every manager and screen model gets tests. Tests use Swift Testing and run on the simulator.

- **Mocks are hand-written, not generated.** Each manager has a `<Name>ManagerTestHelpers` target holding a public `Mock<Name>Manager` that conforms to the protocol, with settable properties and recorded calls.
- **Fixtures** are static factories on the domain types, such as `Forecast.testForecast(...)`.
- **Wiring.** A test registers mocks with `InjectionManager.register`, resets the injection container, and builds the Impl or screen model under test, which picks up the mocks through its ordinary `Inject()` fields. Suites run in parallel and the container is global, so the test is `@MainActor` and does all of that without an `await`, and the Impl resolves every `Inject()` in `init`. `AppEnvironment.test(...)` builds an environment that touches neither the keychain nor the app's documents.
- **Requests.** `StubURLProtocol.makeSession` serves a real `URLSession` from a closure, for testing `NetworkManagerImpl` itself. Everything else uses `MockNetworkManager`.
- **What to cover.** Manager logic and state changes, `Domain.init(response:)` parsing against recorded Open-Meteo payloads, user isolation across a container reset, and screen model loading and error translation. Views are checked with previews.

`make test` runs every test target on the simulator, through `xcodebuild test -scheme Modules-Package` in `Modules/`; `swift test` can't build modules that import UIKit. Velocity emits `<Name>Tests` as a `.testTarget` with no product, and `<Name>TestHelpers` as a regular target that any test target can import.

## Checklists

**Adding a manager.** `mkdir Modules/Managers/FooManager/{FooManager,FooManagerImpl,FooManagerTestHelpers,FooManagerTests}`; `printf 'injects: _\n' > Modules/Managers/FooManager/.package.yml`; write the protocol with `Property` members and typed-throws methods, and the zero-arg Impl; add `NetworkResources/` with bespoke wire types mirroring the API's JSON; write the mock and the tests; `make modules && make project`.

**Adding a screen.** In an existing or new `<Feature>UI` group with `buildersAuto: true`: `<Screen>Screen.swift` in the API target (protocol plus Builder), `<Screen>ScreenImpl.swift` and `<Screen>View.swift` in the Impl target following the four-piece template, previews for light and dark; `make modules && make project`. Push it from another screen model through its Builder.

**Adding a flow.** A `buildersAuto` group under `Modules/Coordinators/` with a Builder that takes the presentation context; the coordinator builds leaf screens through their Builders and, for gated sequences, a `RequirementCoordinator` node list.

**Adding a dependency.** Add it to `dependencies.yml`, `make pulldeps`, `import` it, `make modules && make project`.

## What is deliberately not here

- Pure SwiftUI navigation (`NavigationStack` across screens, `@Environment` propagation of stores). UIKit hosting is the bet, for navigation maturity and structural session isolation.
- Combine, ReactiveSwift, or any publisher framework. `Property`, `SerialTask`, and structured concurrency cover it.
- Constructor-injected dependencies or a hand-written DI container. `Inject()` fields plus generated registration.
- A hand-maintained Xcode project. XcodeGen owns it.
- Third-party networking or image loading libraries.
- SwiftData. Tabular data is in Slate.
- Generated mocks. Mocks are hand-written.
- Real authentication. A username is the whole sign-in, because the point is per-user environments, not auth.
- Slate migrations. Every store is a `.cacheStore`, even for user-created data.
- Release scripts and CI. This is a demo, built and run from Xcode.
